# P5 · 干预节奏控制与反馈回流

> 前四期解决的是"能不能给出建议"。这一期解决的是**什么时候不该给**，
> 以及**用户说了「不要再提」之后，系统是不是真的记住了**。
>
> 这两件事决定它是"助手"还是"监工"。

---

## 1. 为什么必须有节奏闸门

P4 的定位是「有建议就发」。那对演示是对的，对长期使用是灾难：
一个每改一次日程就弹卡片的助手，三天后就会被关掉。

节奏闸门是**防负罪感机制**的落地点。它只回答一个问题：
"现在发，用户会觉得被帮到，还是被打扰？"

---

## 2. 三个参数（唯一取值来源：`backend/app/core/constants.py` §5）

| 参数 | 常量名 | 值 | 出处 | 含义 |
|---|---|---|---|---|
| 冷却期 | `INTERVENTION_COOLDOWN_MINUTES` | 45 分钟 | 文档 B4 | 距上一次**送达**不足此时长，自动触发一律不发 |
| 每日上限 | `INTERVENTION_DAILY_LIMIT` | 3 条 | 文档 B5 | 本地一天内自动送达的干预条数上限 |
| 降权阈值 | `INTERVENTION_MUTE_THRESHOLD` | 3 次 | 文档 B6 | 同一 `decision_type` 被忽略累计达此数后彻底闭嘴 |

**业务代码零字面量**：`services/rhythm.py` 里没有一个数字不是从这里导入的。
答辩现场想调"它是不是太烦了"，改这三个数即可，不必读懂闸门算法。

同段还有两个配套常量：

- `RHYTHM_BYPASS_TRIGGERS = {"manual"}` —— 只有这一个触发类型能绕过闸门；
- `RHYTHM_IGNORE_FEEDBACKS = {"snooze", "mute"}` —— 计进"被忽略"的反馈类型。

### 两条容易被忽略的取舍

1. **手动触发绕过闸门，但仍刷新冷却时钟。**
   用户主动点「问决策器」时被「今日额度已用完」拒绝，是在惩罚用户使用产品；
   但点完之后不该立刻又弹出一条自动干预，所以手动同样把冷却时钟推到 45 分钟后。
   实现上：`manual` 的干预 `metered=False`（不占额度），但仍进入冷却期计算。

2. **每日额度按「本地日」重置，不是按 24 小时滚动。**
   用户心里的一天是"今天"。用 `core/time.containing_local_day` 判定，
   重置点是次日本地 00:00。

## 3. 闸门的两道检查点

闸门不能只放在一个地方 —— 因为**能不能发**这件事在两个时刻的答案不同。

| 时机 | 检查内容 | 为什么在这里 |
|---|---|---|
| 调用模型**之前** | 冷却期 + 每日上限 | 被拦下时一次调用都不烧 |
| 决策产出**之后** | 该 `decision_type` 是否已被降权 | 只有拿到 `decision_type` 才知道该不该发 |

第二道是**兜底**，正常路径不会触发：被降权的类型已经写进 prompt 的负面清单，
模型自己就不会再提。只做第一道不做第二道的话，用户点过三次「不再提醒」之后
还有可能弹出来 —— 不可接受。

## 4. 反馈回流：一次 mute 的完整落地链

```
用户点「不再提醒这类」
 └─> POST /api/interventions/{id}/feedback  {kind: "mute"}
      ├─> 落 intervention.feedback / feedback_at
      ├─> 写一条 BehaviorEvent（intervention_ignored）
      │      └─ 事件流是模型观察用户的唯一窗口，所以反馈必须同时进事件表
      ├─> 同类忽略计数 +1
      ├─> 达阈值 -> muted_intervention_types
      ├─> 下一次 build_request 把它写进 UserProfile
      ├─> render_user_prompt 渲染成「已被用户彻底降权的干预类型」
      └─> 模型本轮不再输出该 decision_type
           （万一还是输出了 -> 降权兜底拒发，blocked_by="muted"）
```

**链条里任何一环断了，那次点击就只是数据库里的一个字符串。**

### 怎么证明最后一环真的通了

前六环都是库里的状态变化，唯独"模型有没有看见"只能靠检查
**渲染出来的 prompt 文本**来证明。`tests/test_feedback_loop.py` 里的
`test_mute_reaches_the_prompt` 断言的就是这件事：

```python
assert "## 用户反馈" in prompt
assert "已被用户彻底降权的干预类型" in prompt
assert "reschedule" in prompt
assert "绝不许" in prompt   # 光出现类型名不够，必须明确写出"不许输出"
```

### prompt 里的位置是刻意的

「用户反馈」段放在**硬约束之后、输出格式之前** —— 这是模型注意力最集中的位置。
反馈若只出现在 prompt 开头，长上下文里极易被忽略，
而"用户说不想再看到"是整段 prompt 里权重最高的一条信息。

除了已降权的类型，还会给出两类更细的信号：

- `被忽略但尚未降权的类型：reschedule（2/3 次）` —— 差一次就封杀，让模型有机会换一种说法；
- `曾被用户采纳的类型：nudge×2` —— 正向信号，说明这类建议对他有效。

## 5. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/interventions/{id}/feedback` | `{kind: accept\|snooze\|mute}`，返回更新后的反馈画像 |
| GET | `/api/interventions/profile` | 当前反馈画像（调试与"它为什么不提醒我了"的查询入口） |
| POST | `/api/decisions` | 返回体新增 `delivered` / `blocked_by` / `rhythm` / `trigger` |

`delivered` 与 `triggered` 是两件事：**触发判定通过 ≠ 送达。**
前端据此判断要不要渲染卡片 —— 被闸门拦下时后端没有落干预记录，
渲染出一张点不动的反馈卡片比不渲染更糟。

## 6. 演示脚本（全程无需 API Key）

```bash
# 1. 造一处硬冲突
curl -s -X POST 127.0.0.1:8000/api/records -H 'Content-Type: application/json' \
  -d '{"type":"schedule","title":"部门例会","start_at":"<明天14:00>","end_at":"<明天15:00>","priority":2}'
curl -s -X POST 127.0.0.1:8000/api/records -H 'Content-Type: application/json' \
  -d '{"type":"schedule","title":"写周报","start_at":"<明天14:30>","end_at":"<明天15:30>","priority":3}'

# 2. 问一次决策器 —— 注意返回里的 delivered / rhythm
curl -s -X POST 127.0.0.1:8000/api/decisions -H 'Content-Type: application/json' \
  -d '{"trigger":"manual"}'
# → delivered=true, rhythm={used_today:1, remaining_today:2}

# 3. 点「稍后提醒」—— 冷却时钟从反馈时刻重新起算
curl -s -X POST 127.0.0.1:8000/api/interventions/<intervention_id>/feedback \
  -H 'Content-Type: application/json' -d '{"kind":"snooze"}'

# 4. 立刻再触发一次自动决策 —— 必须被冷却期拦下
curl -s -X POST 127.0.0.1:8000/api/decisions -H 'Content-Type: application/json' \
  -d '{"trigger":"schedule_change"}'
# → triggered=false, blocked_by="cooldown"

# 5. 连续三次 mute 同一类建议
#    （每次都要先造出一条新的 reschedule 干预）
curl -s -X POST 127.0.0.1:8000/api/interventions/<id>/feedback \
  -H 'Content-Type: application/json' -d '{"kind":"mute"}'
curl -s 127.0.0.1:8000/api/interventions/profile
# → muted_intervention_types: ["reschedule"]

# 6. 之后该类建议不再送达
curl -s -X POST 127.0.0.1:8000/api/decisions -H 'Content-Type: application/json' \
  -d '{"trigger":"manual"}'
# → delivered=false, blocked_by="muted"
```

## 9. 与 P4 的分工

| | P4 | P5 |
|---|---|---|
| 关注点 | 能不能产生建议 | 该不该发、发了之后用户怎么说 |
| `source` | llm / cache / fallback | 沿用，新增 `delivered` |
| 宠物情绪 | 确定性仪表盘，与降级无关 | 不变 —— **闸门拦下干预不影响宠物状态** |

宠物走的是同步快路径，节奏闸门拦下的只是"那条建议卡片"，
仪表盘该显示什么还显示什么。这条边界不能被混淆：
**情绪是事实，干预是行为**，前者不该被后者的节奏影响。
