## 0. 一句话结论

旧版是「**宠物养成游戏，附带一个日程表**」——5651 行里大约六成服务于经验/等级/小鱼干/亲密度/形态/成就这套养成闭环。

新版是「**AI 执行教练，宠物是执行力仪表盘**」。

**这两个产品的重心是相反的。** 所以迁移时不能"功能平移"，而要把宠物从「需要喂养的虚拟生命」降维成「读者一眼能读懂的执行状态可视化」。旧版的心情会随时间自然衰减、需要喂食维护；新版的心情是 `f(完成率, 拖延指数, 冲突)` 的即时函数——**它不会因为你不打开网页就变差**。这不是偷工减料，是产品定位决定的：一个会因为你三天没打开而抑郁的宠物，本质是负罪感制造机，与"反拖延"的目标相悖。

### 4.1 旧版的 5 处硬编，新版必须全部改掉

这是本次裁决中信息量最大的发现。旧版 `parse_nl_plan` 的文档字符串自称*"解析不到的部分给默认值"*，具体是这样给的——**每一条都正好撞在你的约束①「不许硬编」上**：

| # | 旧版代码 | 行为 | 新版处理 |
|---|---|---|---|
| 1 | `result.date = (day or date.today())` | 没写日期 → **默认今天** | ❌ 不再默认。标记 `missing: ["date"]`，草稿卡片留置空由用户点选 |
| 2 | `end_min = start_min + NL_DEFAULT_DURATION` | 只写一个时间点 → **默认 60 分钟** | ❌ 不再默认。标记 `assumptions`，卡片上显式列出"结束时间未指定"并允许改 |
| 3 | `if end_min > 23*60+59: end_min = 23*60+59` | 跨天的结束时间 → **静默截断到 23:59** | ❌ 不再截断。新版用绝对 datetime 本来就能表示跨天，此限制纯属旧版分钟数存储的遗留 |
| 4 | 早间钟点无时段词时按凌晨解析 | "3点开会" → **03:00** | ⚠️ 改为 `assumptions` 显式提示："未写上午/下午，按凌晨 03:00 解析" |
| 5 | `re.search(r"每(?:天\|日\|周...)")` | 重复语义 → **当单次计划处理，只加一句 note** | ⚠️ 保持当单次，但需用户确认，不能只在 note 里小字说明 |

**注意第 3 条与 P2 的关联**：旧版那条 `end_min > 23*60+59` 截断，和 P2 修掉的"`23:30→次日01:00` 算成 0 分钟"是**同一个根因的两副面孔**——都是"用当日分钟数表示时间"导致的。新版已经换成绝对 datetime，所以 NL 层不仅能正确表达跨天，`no_buffer`/`overlap` 检测也自动对接得上。

**另一个容易被忽略的红利**：约束②（草稿卡片）与约束①（不许硬编）是**互相成就**的。正因为中间多了"确认"这一步，"不静默替用户做决定"才变得可行——缺失字段可以大方暴露给用户补。若像旧版那样解析完直接蹦预览但还是要用户手动改，或干脆直接入库，"不许硬编"就会变成难用。

### 4.2 建议放入 P3（主体）与 P4（LLM 增强），理由

**结论：主体放 P3，LLM 兜底分支放 P4。不建议整体推到 P4。**

| 理由 | 说明 |
|---|---|
| **① 「纯规则 + 明确报错」本身就是一个自洽功能** | 约束①的链路是「规则 → 不确定才 LLM → 不确定则 error」。这意味着**只实现前半截就已经可用**，LLM 是增强而非前置依赖。等 P4 才动，等于把能提前一期交付的东西压后 |
| **② 切分点正好落在"数据源"上，不落在功能上** | P3 交付规则解析器；P4 只需在解析器出口加一个分支（`if status == NEED_LLM: → adapter`）。**两边产出同一个 `NLParseResult` schema**，P4 不改 P3 已写好的任何接口。这是最干净的分期切法 |
| **③ 它是 UI 功能，天然属于 P3** | 「输入一句话 → 出草稿卡片 → 点确认」本质是前端交互流程。P3 的主题就是"前端与实时通道"，放这里有归属感 |
| **④ 给 P3 一个面向用户的亮点** | P3 现有验收（双标签页同步、SSE 断连重连、六档表情）全是技术指标，答辩时"两个标签页数据同步了"很难打动人。而一句话「明天下午3点到4点半开组会，高优先级」秒变一张卡片，是**全场最好演示的一个交互** |
| **⑤ 约束④宜早验证** | 约束④要求入库后复用既有冲突检测 + 宠物更新链路，不得另起。`P2` 已经把 `services/state.py` 的钩子建好了，越早接上去试，越能验证那条链路真的是通用的、而不是为表单界面特设的。拖到 P4 才发现钩子不对，返工成本更高 |
| **⑥ 反过来，整体推到 P4 会挤压那一期的核心** | P4 要落地 LLM adapter、10 条输出校验、L0–L4 降级。NL 塞进去会挤掉降级工作，而且 P4 的验收是"**现场拔网线仍出方案**"——加了 NL 会让这条验收难以隔离验证（到底是 NL 挂了还是决策器挂了？分不清） |

**P4 阶段只补两件事：已完成。** ① `NEED_LLM` 出口已接到 `llm/provider.py`（`services/nl_llm.py`）；② LLM 的 NL 输出套上了同样的护栏：区间合理性、起止顺序、跨度上限、优先级夹取，不通过即退回 `need_user`/`error`。**对外 schema 未改一个字段，前端草稿卡片未改一行代码。**

### 4.3 接口（`docs/11-自然语言录入.md` 有完整版）

**只新增 1 个接口** —— 约束④要求入库路径不得另起炉灶，确认草稿时**复用既有的 `POST /api/records`**。

```
POST /api/parse          自然语言 → 草稿（只解析，绝不写库）
```

请求：
```json
{ "text": "明天下午3点到4点半评审PR",
  "now": "2026-10-28T23:00:00+08:00" }
```
`now` 可选，缺省取服务端时钟。**必须可由调用方注入**，否则纯函数不可测（照 P2 对 `conflict/signal/pet` 的同样约定）。

响应 `NLParseResult`：
```jsonc
{
  "status": "resolved" | "need_user" | "error",
  "source": "rule" | "llm" | "cache",   // P3 只有 rule / cache(DEMO 回放)
  "draft": {
    "title": "评审PR",
    "start_at": "2026-10-29T07:00:00Z", // null 表示未识别
    "end_at":   "2026-10-29T08:30:00Z",
    "priority": 3                        // int 1-5
  },
  "missing": ["end_at"],                 // 无依据，卡片留空
  "assumptions": [                       // 推断，卡片标黄
    { "code": "period_inherited", "label": "结束时间按『下午』理解", "field": "end_at" }
  ],
  "confidence": 0.9,
  "error": null                          // { code, message, hint } | null
}
```

> **落实现契约时做了两处改动**（原提案见版本历史）：
> ① `draft` 字段名用 `start_at` / `end_at` 而非 `start` / `end` —— 与 `RecordCreate` 完全同名，
>   因此确认时 `draft` **可直接整个塞进 `POST /api/records`**，无需任何字段映射，也更难写错。
> ② `assumptions` 改为 `{code, label, field}`：稳定 `code` 便于前端按代号本地化，
>   `label` 直接就是给用户看的文案。原提案的 `value` 冗余（值已在 draft 里）。

配套约定：

- **`status` 三态是刻意的设计**，它取代了旧版"给默认值"的做法：`resolved`=可直接确认、`need_user`=缺字段待补、`error`=自相矛盾无解且已附修复建议。
- **`NEED_LLM` 是解析器内部的分派信号，不出现在对外 schema 里**（这是把它拆成 P3/P4 两期却不用改契约的技术根据）。P3 阶段规则判定为该状态时，直接降级为 `need_user` 或 `error`；P4 接上 `llm/adapter.py` 后，同一状态改为真去调模型，拿回结果再以 `resolved`/`need_user` 返回并用 `source: "llm"` 标明出处。**对外契约在 P3 与 P4 完全一致。**
- **`missing` 与 `assumptions` 的区别**：前者卡片上**留空**让用户填，后者**预填但标黄**让用户改。两者都必须渲染出来，不允许静默。
- **`source: "llm"` 在 P3 不会出现**，字段先占好位；**P4 已接入**，清单外的句子开始返回 `source: "llm"`，前端据此显示"AI 补全"标签。
- **校验规则 NXC-1~4**（草稿返回前对 `start`/`end` 强制执行，P3 即生效）：
  1. `start < end` 必须成立（旧版此处用 `+12h` 兜底，仅接受显式午间跨越，其余报错）；
  2. `end - start` 落在合理区间（≤ 24h），**跨天时 `start`/`end` 必须各自带明确日期**（约束③），不接受"只给钟点让人猜"；
  3. 时间戳不得落在不合理绝对区间（如下于 2000 年、超未来 +2 年），防 LLM 幻觉或规则误匹配；
  4. `priority` 必须为 `int 1..5`，`title` 去空白后非空。

## 5. 宠物系统

旧版宠物是**养成游戏**：经验/等级/心情/亲密度/小鱼干/形态/关系阶段，七个维度互相耦合。新版是**仪表盘**：一个六档情绪 + 一个 `energy` 标量。

| 功能 | 旧版行为 | 新版状态 | 决策理由 |
|---|---|---|---|
| 情绪状态机 | 4 档：`normal` / `happy` / `sad` / `hungry`，由「逾期数 + 冲突 + 超载 + 空档」驱动 | ✅ 已迁移并扩展（P2） | 新版六档 `alert`/`dormant`/`tired`/`guilty`/`great`/`normal`，且严格区分**前瞻**（alert=未来 24h 有冲突）与**回顾**（tired=已连续拖延）信号源，旧版此处是混用的 |
| 情绪 vs 台词分离 | ❌ 未分离：模板变量拼接决定说什么 | ✅ 已迁移（P2 计算 / P4 台词） | 核心架构决策，见文档 §5.3「情绪是仪表盘，LLM 是大脑与台词」。**即使 LLM 挂掉，情绪依然准确** |
| 经验 / 等级 | `pet_exp_need`：40/60/80…，完成+10，按时+5，可升级 | ⛔ 有意移出 v1.0 | 等级是"养成"叙事的核心，却是"教练"叙事的噪音。用户升级的动机与"今天把事做完"无关 |
| 心情随时间衰减 | `tick_mood`：平时 0.03/分、有逾期 0.30/分，下限由亲密度抬高 | ⛔ 有意移出 | **这是最需要解释的一条。** 旧版心情会因为你不打开程序而变低——这是游戏化的"回来看看我"钩子，但对拖延者而言它是**惩罚机制**。新版 `energy` 是即时重算，三天不打开再回来看到的是真实状态，不会因为离开而变差 |
| 离线追补衰减 | `_catch_up_offline`：离线每小时掉 3 点，上限 60 | ⛔ 有意移出 | 同上，纯属负罪感增强器 |
| 亲密度（只增不减）4 阶段 | 陌生/熟悉/黏人/形影不离，阈值 20/50/80 | ⛔ 有意移出 v1.0 | 长期陪伴指标，与"今天的执行力反馈"无关。若 v1.1 要做留存钩子，这是最好的候选之一 |
| 小鱼干经济闭环 | 完成掉落 1~3 条（8% 概率稀有 +3）→ 喂食消耗 3 条换心情+12 | ⛔ 有意移出 v1.0 | 完整的小游戏，工作量和叙事价值都不错，但会**稀释"AI 决策器"这个参赛主题**。评委记住的是"AI 分析了我的拖延模式"，不是"我喂了猫" |
| 抚摸互动 + 30s 冷却 | 点不同部位（头/身/尾）不同反应 | ⛔ 有意移出 v1.0 | 纯陪伴向，与执行力无反馈关系 |
| 形态养成 | 关键词归类标题 → scholar/sport/night/plain，倾向分 ≥6 成型 | ⛔ 有意移出 v1.0 | 很有趣，但形态反映的是"你在做什么类型的事"，不是"你执行得好不好"，与仪表盘职责冲突 |
| 多帧动画 / 图片素材 | `assets/pet/<形态>/` 多帧轮询，缺失时回退大号 Emoji | 🔨 P3（改为 SVG） | 复用旧素材需解决版权/格式/打包问题；SVG + CSS 动画无素材依赖、任意缩放，且便于按六档调色 |
| **主动提醒（干预）** | 逾期 / 冲突 / 超载 / 空档 四类，一轮只说一句 | 🔨 P5 | 新版由 LLM 生成干预内容，但**节奏控制（冷却/日上限/降权）必须照搬旧版的硬约束**，否则模型会把产品变成每 10 分钟弹窗的说教机器 |
| 提醒节奏控制 | 冲突只在"刚出现或变多"时提一次；空档每日 ≤2 次且间隔 ≥60 分；超载每日 1 次 | 🔨 P5（见 `may_deliver`） | 旧版这套节奏控制是这个项目里最被低估的资产，必须完整继承 |
| 宠物日记 | `write_diary`：模板拼句（完成情况+逾期+连续天数+自身状态），每天一条存 `pet_diary.json` | ⛔ 有意移出 v1.0 | **v1.1 由 LLM 重做价值极高**——模板拼句的信息量远低于模型归因，这是 LLM 最能出彩的落点之一 |
| 宠物属性面板 | 进度环 + 等级/亲密/心情/连续天数统计卡 | 🔨 P3 | 展示 `mood` + `energy` 即可，比旧版七维面板更能一眼读懂 |
| 重置宠物 | 右键 → 确认 → 回 Lv.1 | ⛔ 有意移出 | 无养成数值可重置 |
