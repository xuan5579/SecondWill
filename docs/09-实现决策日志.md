## 1. B10：`thinking` 与 `json_object` 能否同用

跑到最后一行代码之前，这一项一直是"待实测"。探测脚本 `scripts/probe_llm.py`
依次打四种组合，结果如下（模型 `deepseek-flash`）：

| 组合 | HTTP | 结论 | 耗时 | tokens（推理） |
|---|---|---|---|---|
| A · `json_object` 单用 | 200 | ✅ 合法 JSON | 3.22s | 629（218） |
| B · `json_object` + `thinking=enabled` | 200 | ✅ 合法 JSON | 2.36s | 560（116） |
| C · provider 侧 `json_schema` | **400** | ❌ `This response_format type is unavailable now` | — | — |
| D · 无 `response_format`（基线） | 200 | ✅ 合法 JSON | 3.96s | 883（504） |

**结论：能同用。** 但代码里**不传** `thinking`，理由不是"不能用"，而是"没必要"：
A 组（没传 `thinking`）的响应里同样带 `reasoning_content` —— 这个模型默认就在推理。
多传一个字段就多一个失败面（换模型、换端点时它可能直接 400），收益却为零。
后来第 3 节的分组实测也印证了这一点：开与不开，成功率没有可观测差异。

C 组 400 确认了架构 §4.5 的假设成立 —— **校验层是强制路径，不是锦上添花**。

顺带确认了模型清单（`GET /models`）：该账号只开放 `deepseek-flash`
（= DeepSeek-V4.1-Flash，上下文 1M）与 `deepseek-v4-pro`。
`.env.example` 里沿用的 `deepseek-chat` 是退役写法，写上去直接 400，已更正。

## 2. 第一次录 fixture：两个场景退化成 `fallback`

`python scripts/record_demo.py --clean --decisions --nl-llm` 的输出里，
三个决策场景有**两个**是 `source=fallback`。同一份代码在测试里全绿，
说明卡住的是真实链路、测试覆盖不到的地方。

排查顺序：

1. 先修了一个真 bug：`scripts/record_demo.py` 用 **aware** 的 `datetime.now(timezone.utc)`
   去喂 `build_request`，而契约里 `triggered_at` 的类型是 `UtcDT`（naive UTC）。
   指纹相对化时直接 `TypeError: can't subtract offset-naive and offset-aware datetimes`。
   测试用的是 naive 数据，所以这条路径从来没被测到过。
   修法是统一走新的 `_utc_naive_now()`，而不是在 `_relativize` 里做兼容 ——
   **契约被违反时应该让调用方改，而不是让被调用方兜住所有形状**。
2. 修完仍然 fallback。开日志一看：`LLM 调用失败（truncated）→ 提高到 2048 重试`。
   也就是说 `max_tokens=1024` 一定不够。推理 token 与输出**共用这个额度**。
   于是把默认从 1024 提到 2048（`config.py`），重试档从 2048 提到 4096（`constants.py`）。
3. 改完三个场景全部 `source=llm`。

但"全部变绿"不等于"质量好"，于是继续量了一次失败分布（6 次裸调用 + 5 次完整编排），
结果写进了 §6.2：裸调用 6 次里 **0 次一次通过**，编排后 5 次里仍有 **2 次 fallback**。

## 3. 三问三答：空 content 到底是什么

我当时的结论是"空 content 不重试，吃掉 40% 决策质量"，建议加重试。
这个判断被追问后证明是**错的**，过程如下。

### ① 实测时 `thinking` 是开是关？B10 结论如何？

**关。** 代码里 `provider.complete_json` 只发 `response_format`，从没发过 `thinking`。
B10 结论见第 1 节：可以同用，但默认已推理，故不传。

追问"如果开着就先关掉重测"——本来就是关的，但顺手做了对照实验（重 prompt 各 5 次）：

| 组 | 成功 | 截断/空 | 推理 token 区间 |
|---|---|---|---|
| 不传 `thinking`（现状） | 2/5 | 3/5 | 1248 ~ 2048 |
| `thinking=enabled` | 3/5 | 2/5 | 853 ~ 1808 |

没有可观测差异，与"默认就在推理"的判断一致。

### ② 那 2 次空响应的 `finish_reason` 是什么？prompt 里有 `json` 字样吗？

这是关键一问。之前的 `provider` 在 content 为空时直接抛 `LLMError(EMPTY)`，
**没留下 `finish_reason` 和 usage** —— 我据此把它当成了官方说的"偶发空响应"。
于是绕过 provider，直接打原始接口重测：

```
A-现状/重prompt   空!   fr=length  len=0    tok=2048/推理2048
A-现状/重prompt   空!   fr=length  len=0    tok=2048/推理2048
A-现状/重prompt   截断  fr=length  len=938  tok=2048/推理1608
```

**空 content 的 `finish_reason` 是 `length`，`completion_tokens == max_tokens == 2048`，
`reasoning_tokens == 2048`。** 也就是说：模型把 2048 个 token **全部烧在推理上，
一个输出 token 都没剩下**。所谓"空响应"根本不是玄学偶发，
而是 **`max_tokens` 不够的极端形态** —— 麻烦的是它和"截断"是同一个病，只是程度不同。

prompt 里 `json` 字样**有，而且不止一处**：system 提示要求"只输出一个 JSON 对象"，
user 提示里给了完整的 JSON 格式示例（`PAYLOAD_EXAMPLE` 的 `json.dumps`）。
所以不是 JSON 模式没生效的问题，快照见 `docs/prompts/decision_prompt_snapshot_2026-10-29.md`。

### ③ 系统性还是随机？

**系统性，且与 prompt 规模强相关。** 同一批数据：

| prompt | 记录条数 | 结果 | 推理 token |
|---|---|---|---|
| 种子库 manual（2589 字符） | 10 | 5 次中 3 次失败（2 空 + 1 截断） | 1248 ~ 2048 |
| 拖延场景 | 1 | 2/2 成功 | 264 ~ 457 |
| 过载场景 | 5 | 2/2 成功 | 781 ~ 932 |

轻 prompt 从没失败过。**推理 token 花多少，取决于要处理的记录有多少条**，
而额度是写死的常量 —— 这个组合必然导致"数据越满越容易降级"，
恰恰是演示时最不能出的状况（演示库就是满的）。

### 验证性实验：抬到 4096 再跑 5 次

```
max_tokens=4096 fr=stop len=1077 tok=1639/推理1111  8.44s valid=True
max_tokens=4096 fr=stop len=1336 tok=1811/推理1175  8.86s valid=True
max_tokens=4096 fr=stop len=1075 tok=2728/推理2194 12.89s valid=True   ← 推理 2194 > 2048
max_tokens=4096 fr=stop len=1255 tok=1867/推理1295  8.82s valid=True
max_tokens=4096 fr=stop len=1220 tok=2203/推理1601 11.21s valid=True
```

**5/5 成功。** 第三行尤其说明问题：那次推理用了 2194 token —— 在 2048 的额度下它必死。

`max_tokens` 只是**上限**，不是预购的额度；抬高它不为成功响应多付钱，
只是不再把"思考得久一点"的请求判成失败。

## 4. 落地结果（D1′ + D2′ + D3，2026-10-29 已实施）

原 D1「空 content 重试一次」**已作废** —— 空响应的成因是额度不足，

### 4.2 `dismiss` 为什么是 `snooze` 而不是 `mute`（评审时改掉的一条）

我最初写的映射是 `dismiss → mute`，理由是"dismiss = 不要了"。这个判断是错的：

- `snooze` 是一次性的"这次先不了"；
- `mute` 会写进 `UserProfile.muted_intervention_types`，是**永久降权**（P5 反馈回流），
  且会同时进 prompt 的负面清单 —— 用户从此再也看不到这一类建议。

模型用词本就随意，**因为一个词把用户永久屏蔽掉，这个错误不可逆**。
所以在 `llm/normalize.py` 里立了一条硬规则：**同一个词在两个枚举值之间摇摆时，
选后果更轻的那个**，并把 `ignore`、`stop`、`normal`、`habit` 这类真正摇摆的词
**刻意不映射**（列在 `_AMBIGUOUS` 里，附理由）—— 猜错会静默污染数据，
而让它校验失败、把原文回传给模型重试，至少是显式的，且模型通常一次就改对。

## 6. prompt 裁剪第一刀：`MAX_RECORDS` 40 → 14 + 相关度排序（2026-10-30 实施）

**先修正一个被实测推翻的判断。** §6.2 时写的是"40 条记录几乎必然撞顶 8192"；
2026-10-30 用合成满日程数据实测后，这个说法**不成立**：

| 数据集 | prompt 字符 | 记录条数 | 推理 token（3 次） | 撞顶 |
|---|---|---|---|---|
| 满日程（冲突明确、有空档） | 4000 | 25 | 312 ~ 501 | 否 |
| 同上，裁剪后 | 3464 | 14 | 91 ~ 442 | 否 |
| **满量极限**（两天排满+逾期+完成） | 4925 | **40** | 374 ~ **870** | **否**（fr=stop，一次过 3/3） |

原始输出：`docs/prompts/prompt_trim_probe_2026-10-30.json`、
`prompt_trim_probe_40_2026-10-30.json`。

**撞顶的主导因素是内容歧义度，不是条数**：种子库 9 条"真实感强"的记录
能烧到 2737 推理 token，40 条"决策简单"的合成记录只要 870。
条数增长抬高的不是推理的"下限"而是"歧义面的上限" ——
条数越多，可考虑的组合越多，最坏情况越坏。

那这一刀还该不该裁？**该，理由变了但没变弱：**

1. **给最坏情况封顶。** 4096 额度下，"40 条 × 高歧义内容"的组合仍可能超限
   （9 条高歧义就已到 2737）；把条数压到 14，等于把歧义面从 40 份缩到 14 份。
   这比"继续加额度到 8192"便宜 —— 额度加上去，**每次调用**的延迟上限都跟着涨。
2. **无关条目本来就只亏不赚。** 已完成/远期条目对"这次要不要干预"没有信息量
   （完成率等信号已单独给过模型），却占着 prompt 稀释注意力。
3. **排序是裁剪的配套，不是可选项。** 按库序切前 14 条，可能恰好把正在冲突的
   两条切掉 —— 模型连决策对象都看不到。所以截断必须发生在相关度排序之后：

   层 0 硬冲突对 → 层 1 软冲突 → 层 2 逾期未完成 → 层 3 未来 24h 内
   → 层 4 远期 → 层 5 已完成/已放弃（`orchestrator._rank_records`）。

改动面：`core/constants.py` 一个默认值 + `orchestrator.build_request` 截断前排序；
`tests/test_prompt_trimming.py` 8 项钉住"冲突对必留、已完成必剔除、确定性"。

**顺带发现并修掉的一个隐蔽缩进错误**：`decide()` 里 `DEMO_MODE` 分支的
`outcome = await _call_with_retry(...)` 在上轮 D2′ 编辑时掉出了 `else` 块 ——
DEMO 模式下未命中 fixture 会先 `NameError`（`stats` 未定义）而不是规则降级。
之前没暴露是因为：测试全走 `DEMO_MODE=false`，DEMO 回放又 3/3 命中不走该分支。
演示模式的红线（"绝不能偷偷真调"）差点就是虚的，好在 `stats` 未定义让它在
真正发起调用**之前**就炸了。已修复并保留该分支的注释。

**仍然保留的第二刀（未做，等真出现再动）**：`tags` 字段对决策几乎没有信息量，
可整列去掉；按记录条数动态给额度仍不建议 —— 复杂度收益比太差。

## 7. 兜底的对抗性验证：不能等答辩现场才第一次触发（2026-10-30）

D 组上线后跑了 6 次真实调用，归一化**一次都没触发**——主力 prompt 把跑偏
全拦在了前面。但"从没触发过的兜底等于没有兜底"，所以手工构造坏响应喂进
完整编排器（`tests/test_normalize_adversarial.py`，4 项）：

1. **接得住**：`time_conflict`→`conflict`、`dismiss`→`snooze` 的输出**一次通过**
   校验（`source=llm`、单次调用，不耗重试），好坏枚举混排时只动错的那几个；
2. **留得下痕迹**：模型原始值进 WARNING 日志（`caplog` 断言原文出现），
   同时以 `[规则3/ok]` 回传进 `DecisionResult.issues`；
3. **拿得准轻重**：`ignore` 这类摇摆词**刻意不映射** → 第 1 次 L1 失败 →
   编排器把 Pydantic 错误原文（字段路径 + 允许值清单）回传 → 第 2 次写对。
   断言确认日志里**没有**任何关于 `ignore` 的映射记录。

一个意外收获：我第一版测试词用了 `schedule_clash`——不在映射表里——
于是它真的 L1 失败了。这恰好从反方向证明**表外词不会被瞎猜**，
该失败就失败，这条"事故"值得留着当文档。

### 7.1 顺手揪出的两个既有 flaky（上午跑全量回归时暴露）

`test_record_change_triggers_decision_in_background` 与
`test_snooze_blocks_the_next_auto_trigger` 用"明天 14:00"造冲突对。
但 `should_trigger` 只认 `[now, now+24h]` 窗口内的冲突——**上午 10 点跑，
"明天 14 点"在 27.5h 之外，冲突不可见，自动触发不成立**；14 点后跑才通过。
前几轮全绿只是因为都在晚上跑。同文件的 `test_pet_mood_is_reported_alongside`
注释里其实早就写了"可能落在窗口外"，但没人把它当失败风险。

修法：换成"从 now 起至少 2h 后、本地 08:00~21:00 内的最近整点"，
必然 ≤10h，任何时刻跑都稳定落进窗口；同时清除已无人调用的 `_tomorrow`。

教训与 §5 同源：**"测试通过"只说明"在那个时刻、那个入射角下通过"**。
凡是用真实时钟 + 固定墙上时间造数据的用例，都要问一句"换 12 个小时跑还成立吗"。

### 7.2 测量脚本里踩的一个 Python 语义坑（无产品影响，值得记）

`render_user_prompt(req, max_records=LLM_PROMPT_MAX_RECORDS)` 的默认参数
是**定义时求值**的——运行时改模块常量对已定义的函数不生效，测 A/B 对比时
A 组被悄悄二次截断，两组 prompt 字符数几乎一样，第一版对比数据完全作废。
结论：默认参数引用可变环境的模块常量时，要么显式传参，要么把默认设为 `None`
在函数体内读常量。
