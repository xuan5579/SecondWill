### 状态三种取值

| status | 含义 | 前端表现 |
|---|---|---|
| `resolved` | 起止时间都拿到了，可直接确认 | 绿标「可直接确认」 |
| `need_user` | 缺字段（通常是缺结束时间），卡片留空待填 | 黄标「待补充」，缺失字段描黄边 |
| `error` | 自相矛盾或规则层无解，**附修复建议** | 红卡 + 具体 hint |

`need_user` 不是失败。它表示"这句话我读懂了，但有些信息你没说" —— 卡片会补齐所有已识别的字段，只把没依据的留白。

## 2. 明确不支持的写法

清单外一律返回结构化错误，**不猜测、不兜底**。

| 输入 | 返回 |
|---|---|
| `月底前交季度报告` | `NXC-NEED-LLM`｜规则层无法可靠解析 |
| `下周抽空做复盘` | `NXC-NEED-LLM`｜『抽空』无确定语义 |
| `明天上午10点开会然后下午3点写文档` | `NXC-NEED-LLM`｜一句话多件事 |
| `明天上午9点到8点开会` | `NXC-1`｜结束早于开始 |
| `今天晚上11点到1点值班` | `NXC-1`｜跨天但没写结束日期 |
| `明天9点10点11点各一个会` | `NXC-T1`｜出现 3 个时间点 |

### 错误码

| code | 含义 |
|---|---|
| `NXC-NEED-LLM` | 规则层放弃。**P4 接 LLM 后这一类会最先被覆盖**，返回结构不变 |
| `NXC-1` | 时间顺序矛盾（含跨天未写清日期的情况） |
| `NXC-2` | 跨度超过 24 小时，或跨天缺少明确结束日期 |
| `NXC-3` | 绝对年份超出合理区间（防规则误匹配与模型幻觉） |
| `NXC-T1` | 时间点多于 2 个，无法确定构成区间的那两个 |
| `NXC-T2` | 时间点数值不合法 |
| `NXC-D1` | 日期数值不合法 |

每条 error **必须带 `hint`**（已由测试锁定）—— 报错的目的是让用户知道怎么改，不是显示"失败了"。

## 3. 「不许硬编」的具体落地

旧版 `parse_nl_plan` 有 5 处静默兜底，这里逐一重写，且每处都有测试盯着：

| # | 旧版行为 | 新版做法 |
|---|---|---|
| 1 | 没写日期 → 默认今天 | 预填今天，但进 `assumptions`（`date_default_today`）标黄 |
| 2 | 只有一个时间点 → 默认 +60 分钟 | 进 `missing`，卡片留空。**不替用户假设时长** |
| 3 | 跨天 → 静默截断到 23:59 | 绝对 datetime 天然支持跨天；但没写清结束日期就报错 |
| 4 | "3点开会" → 03:00 且不吭声 | 按字面理解，但进 `assumptions`（`no_period`）提示 |
| 5 | 重复语义只加一行小字 note | 不支持，直接 `NXC-NEED-LLM` |

### `missing` 与 `assumptions` 的分工

这是整套设计的核心：

- **`missing`** = 毫无依据 → 留空白给用户填
- **`assumptions`** = 有约定俗成的解读 → 预填但必须标黄告知

之所以要分开：constraint ①「不许硬编」和"好用"表面上是冲突的，中间那层**草稿确认**（constraint ②）正是把两者调和的开关 —— **推断不是不能做，而是必须可见、可改。**

### 已实现的 assumptions

| code | 触发条件 | 提示文案 |
|---|---|---|
| `date_default_today` | 有时间没写日期 | 未提到日期，暂按今天（可直接改） |
| `no_period` | 整句无时段词且起始 ≤ 11 点 | 未说明上午/下午，按 24 小时制字面理解 |
| `period_inherited` | 「下午3点到4点半」的第二个点 | 结束时间按『下午』理解 |
| `week_semantics` | 出现『下周X』 | 下周＝下一个日历周（周一起算） |
| `dom_semantics` | 出现『X号』 | 『30号』按最近的未来日期解析 |
| `cross_day` | 起止落在不同日期 | 跨天日程，已按写明的两个日期分别定位 |

**时段继承有一条关键限制**（`services/naturallang.py` 里有注释）：
只在「按字面理解会导致自相矛盾」时才继承。本来合理的解析绝不擅自改写 ——
`下午2点到3点` 会被继承成 14:00–15:00，而 `上午9点到11点` 保持字面 09:00–11:00 不动。

## 4. 分期切法：为什么两边用同一个 schema

| 期 | 谁算 | `source` 字段 |
|---|---|---|
| P3 | 纯本地正则 | `rule`（DEMO 回放时 `cache`） |
| P4 | 同一套 schema，数据源换成 DeepSeek | `llm` |

**切分点落在"谁来算"，而不是"输出长什么样"。**
`NLParseResult` 与 `NLDraft` 的字段两期完全一致，所以：

- 前端草稿卡片在 P4 **不需要改一行代码**
- `need_user` / `missing` / `assumptions` 这套机制对 LLM 同样有效 —— 模型拿不准的信息也是留空给用户，而不是硬编

P3 阶段 `NXC-NEED-LLM` 如实降级为 `error`；P4 接上 adapter 后同一条 code 改成真去调用模型，返回结构不变。

这条已作为设计决策 D-4 写进架构文档 §0.1。

## 5. DEMO_MODE：录制回放为什么存相对量

常规录制直接存绝对时间戳：今天录下"明天上午9点"= `2026-10-30 09:00`，
三天后回放就是一条**过期日程**，现场穿帮。

所以 fixture 存的是**相对量**，且区分两种锚定方式：

| 锚定 | 例句 | 存储形式 |
|---|---|---|
| 相对 | `明天上午9点` | `day_offset` + `minute` |
| 绝对 | `11月3日下午2点` | `month` + `day` + `minute`（今年，已过则顺延下一年） |

回放时按当时的"今天"重新算绝对值 —— fixture 因此是**常青**的：

```
句子                              今天回放                三天后回放
明天上午9点到11点开会              10-30 09:00~11:00      11-02 09:00~11:00   ← 跟着漂
11月3日下午2点到4点客户拜访         11-03 14:00~16:00      11-03 14:00~16:00   ← 锁死
11月20日23:30到11月21日1:00上线    11-20 23:30~11-21 01:00 同左               ← 跨天两端各自正确
```

指纹只取原文、**不含** `now`，否则每次请求指纹都不同，回放永远命中不了。

> ⚠️ 清单里含 `11月3日`、`12月1日` 这类固定日期例句，其相对偏移会随录制日期变化。
> **建议答辩前一天重录一次**，让这些例句也落到未来日期上。

```bash
DEMO_RECORD=true python scripts/record_demo.py --clean   # 重录（21 条）
DEMO_MODE=true uvicorn app.main:app                      # 演示时开回放
```

## 6. 演示脚本（建议顺序）

1. 点「演示例句」第 1 条 `明天上午9点到11点开会` → 绿卡，直接「确认添加」
2. 第 11 条 `今天晚上11点到明天凌晨1点值班` → **跨零点**，讲旧版算成长度 0
3. 第 3 条 `后天晚上8点看电影` → 结束时间留空描黄边：*这里不替用户假设时长*
4. 第 7 条 `明天9:00到10:30写项目方案` → 出现「未说明上午/下午」推断条
5. 手输 `月底前交季度报告` → 红卡 + hint：*这句留给 P4 的模型*
6. 再添一条重叠日程 → 猫立刻变 ALERT（证明走的是既有链路，没有第二条）
